# Tablestake 투자 피칭 데모

포항 동네 가게(그리고 국내·해외 맛집)에 투자하고, 가게 매출의 일부를 매달 받는 서비스의 시연용 코드다.
OPEN HARBOR 2026 비즈니스톤 IR 피칭(DEMO DAY 11/12)에서 띄우는 용도.

- `backend/`: Spring Boot 3.5, Java 17, JPA, H2(메모리 DB). 투자, 월 정산·분배, 매출 이상 탐지, 모집 한도 심사.
- `frontend/`: React 18, Vite 5, TypeScript. 투자자 앱(휴대폰, 증권앱 스타일), 운영 콘솔, 두 화면을 나란히 띄우는 시연 화면.
- `tools/mock-photos/`: 시연용 음식 그림을 만드는 스크립트. 실제 사진이 생기면 필요 없다.

## 실행

준비물은 JDK 17 또는 21, Node 18 이상(20 LTS 권장)이다.
JDK 25는 쓰지 마. Gradle 8.14가 JDK 25 위에서 돌지 않는다. `java -version`으로 확인하면 된다.

```bash
# 터미널 1: 백엔드 (http://localhost:8080)
cd backend
chmod +x gradlew      # 권한 오류가 날 때만
./gradlew bootRun

# 터미널 2: 프론트 (http://localhost:5173)
cd frontend
npm install
npm run dev
```

브라우저에서 http://localhost:5173 을 열면 시연 화면(왼쪽 휴대폰, 오른쪽 운영 콘솔)이 뜬다.

| 주소 | 화면 |
|---|---|
| `/` | 시연 화면 (발표용) |
| `/app` | 투자자 앱만 (휴대폰 화면 녹화용, 브라우저 폭을 390px로 줄여서) |
| `/admin` | 운영 콘솔만 |
| http://localhost:8080/h2-console | DB 확인 (JDBC URL `jdbc:h2:mem:tablestake`, 사용자 `sa`, 비밀번호 없음) |

- 서버를 켤 때마다 시연 데이터가 새로 깔린다. 발표 중에는 오른쪽 위 **처음 상태로 되돌리기**로 초기화한다.
- 조각 시세·예수금·주문은 브라우저 메모리에만 있다. **휴대폰 화면(iframe)을 새로고침하면 거래 내역이 초기화된다.** 발표 중에는 앱 안의 탭과 뒤로 버튼으로만 움직일 것.
- 첫 실행 때 Gradle과 npm이 라이브러리를 내려받는다. **발표 전날 인터넷 되는 곳에서 한 번 실행해 둘 것.**
- 테스트 실행: `cd backend && ./gradlew test` (27개)

## 투자자 앱 구성 (v2, 증권앱 스타일)

아래 탭 4개. 토스증권(홈 / 시장·실시간 차트 / 종목 상세 / 주문 시트)과 뮤직카우(옥션 / 마켓 발견하기)를 참고했다.

| 탭 | 내용 |
|---|---|
| 홈 | 내 자산(총 자산, 오늘 변동, 받은 돈) → 노란 검증 띠 → **안심하고 투자하는 이유**(카드 매출 대조 n/7곳 일치, 정산 보류 n곳, 가격 천장) → 내 가게 조각 → 모집 중인 공모 → 단골 혜택 → 가게 소식 |
| 마켓 | TABLE 지수(지급 포함 총수익, 1년 전 = 1,000), 지역(전체·포항·국내·해외), 순위 기준(급상승·급하락·거래 많은·연 수익률·매출 성장), 실시간 시세 |
| 공모 | 모집 중인 상품 (1만 원 단위 청약, 만기 보유형 1단계 상품) |
| 내 자산 | 총 자산, 투자 손익(받은 돈 포함), 가게 조각/예수금, 입금·출금(시연용), 월별 받은 돈, 보유 가게(수익률순), **기다리는 주문(작은 X로 취소)**, 단골 인증, 거래 내역 |

가게 화면(지급 중): 사진 → 가격·기간별 차트(1일 실시간 ~ 전체) → 지금 사면 연 수익률 → **가격 천장 막대** → 실시간 체결 → 다음 지급 예상 → 매출 검증(카드 결제 비중 막대 + 월 매출) → 정산 내역(1원 단위 공개) → 위험 등급 → 단골 혜택 → 소식 → 아래 고정 바 **"내 보유 n조각 · 금액 · 수익률 | 판매 | 구매"**.
구매·판매를 누르면 주문 시트가 아래에서 올라오고, 오른쪽 위 **작은 X**로 언제든 닫는다(주문 취소).

## 시연 데이터

날짜는 실행하는 날 기준으로 자동으로 맞춰진다. 가게 이름과 숫자는 모두 가상이다.
포항(실증) → 국내 → 해외 확장 그림을 보여 주려고 세 지역 가게를 섞었다. 해외 가게는 "3단계 확장 예시"로 표시되고, 매출·지급은 원화로 환산해 보여 준다.

| 가게 | 지역 | 상태 | 시연에서 보여 줄 것 |
|---|---|---|---|
| 육거리 돼지국밥 | 포항 | 모집 중 80%, A | 공모 투자하기, 셀프 결제(매출 부풀리기) 탐지 |
| 중앙상가 수제버거 | 포항 | 지급 중, 데모 투자자 50조각 | 월 정산·휴대폰 영수증, 현금 결제 유도 → 정산 보류, 조각 거래 |
| 양덕 쌀국수 | 포항 | 모집 중 30%, B | 외국인 사장님 가게 사례 |
| 한동대 앞 분식 | 포항 | 심사 중 (앱에 안 보임) | 최근 3개월 급등 → 한도 초과 → 심사 보류 |
| 죽도시장 물회 | 포항 | 지급 중, 데모 20조각 | 여름 성수기 계절 변동(이상으로 오해하지 않음) |
| 영일대 브런치 카페 | 포항 | 지급 중 | |
| 성수 베이글 | 국내(서울) | 지급 중, 데모 10조각 | 매출 성장 1위 (전년 대비 +15%) |
| 황리단길 한옥 찻집 | 국내(경주) | 모집 중 55% | |
| 스시 카이 | 해외(도쿄) | 지급 중, 데모 30조각 | 인기 가게: 가격이 높아 "지금 사면 연 수익률"이 낮다 |
| 팟타이 사왓디 | 해외(방콕) | 지급 중, **정산 보류 상태로 시작** (11/12에 켜면 9월분) | 카드 비중 63% → 41%, 위험 C, 가격 하락. 콘솔에서 정산하면 보류 도장 |
| 비스트로 르방 | 해외(파리) | 지급 중 (새로 상장) | |

사진은 `frontend/public/photos/{imageKey}.jpg`이고, 직접 그린 시연용 그림이다. **실제 가게 사진을 같은 이름으로 넣으면 바로 바뀐다.**

## 발표 시연 순서 (약 3~4분)

1. **홈** (휴대폰): 내 자산과 "안심하고 투자하는 이유" 3가지를 먼저 보여 준다. 차별점이 메인에 있다.
2. **공모 투자** (휴대폰): 공모 탭 → 육거리 돼지국밥 → 카드 결제 비중·한도 계산 → 투자하기 10만 원 → 완료. 예수금에서 빠지고, 콘솔 목록의 모집액이 바로 올라간다.
3. **정산** (콘솔): 중앙상가 수제버거 → "정산하기"(11/12에 켜면 9월분) → 61명 분배표와 "나눈 돈 합계 = 투자자 몫". **동시에 휴대폰에 영수증이 출력된다.** 홈의 받은 돈이 늘어난다.
4. **매출 누락 탐지** (콘솔): 같은 가게 월 매출 등록 → "현금 결제 유도" → "카드 결제 비중 급감" 경고 → 다음 달 "정산하기" → **정산 보류 도장** → "확인했어요, 정산 진행" → 휴대폰 영수증에 "확인한 뒤 정산했어요".
   - 시간이 없으면 이미 보류 상태인 **팟타이 사왓디**를 바로 보여 줘도 된다 (앱: 마켓에서 주황 경고 표시, 가게 화면 "정산을 보류했어요" / 콘솔: 정산하기 → 보류 도장).
5. **마켓** (휴대폰): 실시간 순위(급상승·거래 많은·연 수익률), TABLE 지수. "어느 가게가 대세인지" 보이지만, 순위 옆 초록 체크가 "카드 매출로 검증된 가게"라는 점을 같이 말한다.
6. **조각 거래와 가격 천장** (휴대폰): 스시 카이 또는 수제버거 → 차트 기간 바꾸기 → 아래 **구매** → 주문 시트(호가창) → X로 닫아 보이기 → 다시 구매 → 가격에 12,000 입력 → "천장보다 비싸요" 차단 → "왜 천장이 있나요?". 코인처럼 끝없이 오를 수 없다는 설명.
7. **기다리는 주문 취소**: 가격 지정으로 조금 싸게 걸어 둔 뒤 → 내 자산 → 기다리는 주문의 작은 X로 취소.
8. **단골 혜택**: 내 자산 → 단골 혜택 → 인증 (초 단위 시계).
9. 끝나면 "처음 상태로 되돌리기".

조각 거래는 브라우저 안의 모의 시장이라 정산과 연결되지 않는다(산 조각만큼 다음 정산을 더 받지는 않는다).

## 핵심 규칙

| 규칙 | 값 | 코드 |
|---|---|---|
| 지급 | 가게가 매달 신고 매출의 5%를 내고, 정산 수수료 2%를 뺀 금액을 투자금 비율대로 나눈다 | `SettlementService`, `PayoutDistributor` |
| 종료 | 가게가 투자금의 1.3배를 갚거나 60개월 (투자자는 수수료를 빼고 최대 1.274배) | `Offering.applyPayout` |
| 수수료 | 모집 5%(가게 부담), 정산 2%(투자자 몫에서 뺌), 조각 거래 1%(5조각 이상 0.8%) | `FeePolicy`, `market.ts` |
| 단골 혜택 | 상품마다 투자자 혜택, 내 자산의 "인증" 화면으로 매장에서 확인 | `Offering.investorPerk` |
| 모집 한도 | 최근 12개월 평균 매출 × 5% × 60 ÷ 1.3 (의심 달 제외) | `FundingLimitCalculator` |
| 투자 단위 | 1만 원 단위(= 1조각), 1인 한 상품 500만 원까지 | `InvestmentPolicy` |
| 매출 등록 | 마감된 달만, 한 달씩 순서대로 | `RevenueAdminService.registerRevenue` |
| 정산 | 지급 시작 달부터 한 달씩 순서대로, 같은 달 두 번 불가 | `SettlementService.settle` |
| 정산 보류 | 그 달에 "경고" 등급 탐지가 있으면 확인 전까지 보류. 앱 목록에도 같은 규칙으로 "보류" 표시 | `SettlementService.settle`, `OfferingService.holdAlertOf` |
| 가격 천장 | 조각 하나가 앞으로 받을 수 있는 돈(1만 원 × 1.274 − 지금까지 받은 돈)보다 비싸게 살 수 없다 | `market.ts placeOrder` |

이상 탐지 규칙 (`RevenueAnomalyDetector`):

| 탐지 | 조건 | 노리는 수법 |
|---|---|---|
| 카드 매출 > 신고 매출 | 카드사 승인액이 신고액보다 큼 | 신고 누락 |
| 카드 결제 비중 급감 | 평소 비중보다 15%p 이상 떨어짐 | 현금 결제 유도 후 누락 |
| 매출 급등 | 12개월 중앙값보다 20% 넘게 높고 이상 점수 3 이상이면 주의, 30%·4 이상이면 경고 | 셀프 결제로 부풀리기 |
| 매출 급감 | 이상 점수 −4 이하이면서 25% 이상 낮음 | 영업 악화 (주의) |
| 최근 3개월 급등 | 최근 3개월 평균이 그 전 9개월보다 30% 이상 높음 | 모집 직전 부풀리기 |

이상 점수는 중앙값과 MAD(중앙 절대 편차)로 계산한 robust z-score다. 평균·표준편차를 쓰면 튄 달 하나에 기준이 끌려가서 중앙값을 썼다.

## 모의 시장 (`frontend/src/lib/market.ts`)

- **적정가**: 남은 지급(조각당 남은 상한)을 매달 지급액으로 나눠 받는다고 보고, 가게별 할인율(인기 가게일수록 낮음)로 현재 가치를 계산한다.
- **지난 가격**: 실제 정산 이력(지급 시작 달, 마지막 정산 달, 누적 지급)과 매출 성장률로 날짜별 적정가를 다시 계산하고 잡음·분위기를 더했다. 지급일에는 받은 만큼 가격이 내려간다(배당락).
- **지금 가격**: 2.5초마다 다른 투자자의 주문이 호가에 들어오고 체결된다. 내가 걸어 둔 주문도 상대가 오면 체결되고 알림이 뜬다.
- **내 자산**: 예수금 = 시연용 100만 원 ± 거래 − 공모 투자 + 서버 기록상 받은 돈. 투자 손익 = 평가금액 + 받은 돈 − 원금.
- 실제 서비스라면 주문·체결·조각 이전은 서버의 매칭 엔진이 트랜잭션으로 처리해야 한다.

## API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/offerings?status=` | 투자상품 목록 (심사 중은 숨김). 지역·도시·사진, 지급 현황, 정산 보류, 매출 추이 포함 |
| GET | `/api/offerings/{id}` | 상품 상세 (매출, 검증, 한도, 위험 등급, 예상 수익, 원 단위 정산 기록) |
| GET | `/api/offerings/{id}/simulation?amount=` | 투자 금액별 예상 지급 |
| POST | `/api/offerings/{id}/investments` | 투자 `{ "amount": 100000 }` |
| GET | `/api/me/portfolio` | 내 자산 |
| GET | `/api/admin/stores` | 가게 목록 (검증 상태, 위험 등급) |
| GET | `/api/admin/stores/{id}/revenues` | 가게 매출 기록, 한도 심사 |
| POST | `/api/admin/stores/{id}/revenues` | 월 매출 등록 `{ "month": "2026-10", "reportedRevenue": 0, "cardRevenue": 0 }` |
| GET | `/api/admin/offerings/{id}/settlements` | 정산 현황 |
| POST | `/api/admin/offerings/{id}/settlements` | 월 정산 `{ "month": "2026-10", "anomalyConfirmed": false }` |
| GET | `/api/admin/settlements/{id}` | 정산 상세 (투자자별 분배) |
| POST | `/api/demo/reset` | 시연 데이터 초기화 (초기화하면 id가 새로 매겨진다) |

오류는 모두 `{ "code", "message", "details" }` 형식이다. 예를 들어 정산 보류는 `409 SETTLEMENT_ON_HOLD`이고, details에 걸린 경고가 담긴다.

## 면접에서 설명할 포인트

- **정산 동시성**: 같은 상품을 두 명이 동시에 정산하면 이중 지급이 된다. 정산 시작 시 상품 행을 비관적 락(`SELECT ... FOR UPDATE`)으로 잡고, `(offering_id, settlement_month)` 유니크 제약을 마지막 방어선으로 뒀다. 투자도 같은 락으로 모집액 초과를 막는다.
- **1원 단위 분배**: 수수료를 뺀 704,718원을 61명에게 투자금 비율로 나누면 끝수가 남는다. 최대 잔여 방식(largest remainder)으로 내림 후 남은 원을 소수점이 큰 순서대로 1원씩 줘서 합계가 지급액과 항상 같다. (`PayoutDistributorTest`)
- **보류 표시와 실제 보류의 일치**: 앱 목록의 "정산 보류" 표시는 정산 서비스와 같은 규칙(다음 정산 달의 높은 단계 경고)으로 계산한다. 통합 테스트가 "표시된 달은 실제로 정산이 막힌다"를 확인한다.
- **시드 데이터 검증**: 시연 데이터는 실행 날짜 기준으로 만든다. 24개월 어느 달에 켜도 계절 변동·성장을 이상 매출로 오해하지 않는지 단위 테스트로 확인한다(`SeedRevenueGeneratorTest`). 실제로 성장률을 1.5%로 줬더니 특정 달에 매출 급등 경고가 나서 1.0%로 낮췄다.
- **상환 상한**: 마지막 달에는 남은 상한만큼만 지급하고 상품을 지급 완료로 바꾼다. 상한은 가게가 낸 돈 기준으로 세고, 수수료는 그 안에서 뗀다.
- **수익 숫자** (5년, 매달 같은 금액 가정): 투자자 연 약 10.4%, 가게 실제 부담 연 약 13.9% (모집 수수료 포함). 1.4배로 올리면 가게 부담이 연 18%를 넘어 카드론보다 비싸져서 1.3배로 정했다.
- **N+1 방지**: 목록 조회는 `join fetch`로 가게를 함께 가져온다. `open-in-view: false`로 트랜잭션 밖 지연 로딩을 막았다.
- **테스트**: 계산 로직(분배, 수익률, 이상 탐지, 한도, 시드 매출)은 스프링 없이 단위 테스트하고, 발표 시나리오 전체는 `DemoFlowIntegrationTest`로 돌린다.

## 한계 (시연용이라 일부러 뺀 것)

- 로그인 없음. "데모 투자자" 한 명으로 고정이다.
- H2 메모리 DB라서 서버를 끄면 데이터가 사라진다. 실제 운영은 PostgreSQL로 바꾸고 마이그레이션 도구(Flyway)를 붙여야 한다.
- 매출은 콘솔에서 손으로 넣는다. 실제로는 POS, 카드사, 홈택스 연동으로 받아야 한다. 해외 가게는 현지 PG·환율 연동이 필요하다.
- 세금(원천징수)은 반영하지 않았다.
- 조각 시세·체결·예수금은 브라우저 안의 모의 시장이다. 실제로 하려면 서버에 주문·체결 매칭 엔진, 조각 이전 트랜잭션, 체결 동시성 처리가 필요하다.
- 법적 순서(팀 기획안 기준): 1단계는 거래 없이 만기까지 보유하는 상품으로 공모한다(투자계약증권, 증권신고서. 뱅카우 방식). 사고팔기는 조각투자 장외거래소가 열리면 연동하는 2단계다. 해외 투자자·해외 가게는 3단계로, 현지 법인이나 현지 플랫폼 제휴가 필요하다.

## 폴더 구조

```text
backend/src/main/java/com/tablestake
├── offering     투자상품, 예상 수익(IRR), 목록·상세·시뮬레이션 API, 정산 보류 표시
├── investment   투자, 내 자산, 투자 정책(단위·한도)
├── settlement   월 정산, 투자자별 분배
├── store        가게(지역·도시·사진), 월 매출, 분석(위험 등급, 모집 한도, 검증 상태, 성장률)
├── anomaly      매출 이상 탐지 규칙
├── admin        운영 콘솔 API (매출 등록, 정산)
├── demo         시연 데이터 생성, 초기화
└── global       예외 처리, 시간(Clock), 통계 유틸

frontend/src
├── stage        시연 화면 (iframe 2개)
├── app          투자자 앱: 홈, 마켓, 공모, 가게(차트·주문 시트), 투자하기, 내 자산, 단골 인증, 정산 영수증
│   └── ui       사진, 등락 표시, 가격 차트, 알림, 아이콘
├── admin        운영 콘솔 (정산, 매출 등록, 한도 심사, 매출 기록)
├── components   간판, 상태 배지, 매출 그래프, 진행 막대 (콘솔과 함께 씀)
└── lib          API 호출, 타입, 금액 표기, 화면 간 동기화, 모의 시장(market), 내 자산 계산(account), 가게 소식(news), 연출 값(catalog)
```
